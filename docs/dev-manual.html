DuoGrow Developer Manual

An AI accountability app for exactly two people. You pair with one person, do real things, upload proof, and AI verifies it — a shared dashboard, duo streak, and growth score update live for both of you. This manual documents how the app is actually built.

01What this is

DuoGrow is a two-package TypeScript monorepo: a Hono + better-sqlite3 API and a React 19 + Vite single-page app. In production a single Node process serves both the API and the built SPA from one origin, so there is no CORS layer anywhere in the codebase.

Server

Hono 4.12.31 on @hono/node-server, better-sqlite3 12.11.1, run through tsx. No build step — TypeScript executes directly.

Web

React 19.2.7 + react-router-dom 7 (HashRouter), built by Vite 8. Styled with hand-written CSS — no UI framework.

Data

One SQLite file plus an uploads folder under DATA_DIR. WAL mode, foreign keys on.

Runtime

Node >=22.9 is a hard requirement — the start scripts use --env-file-if-exists.

02Quick start

Three installs, because the root, server, and web each have their own lockfile:

npm install
npm --prefix server install
npm --prefix web install

npm run seed     # demo duo: Sreya + Sai, 7 days of history
npm run dev      # web :5173, api :8787

Sign in with the seeded demo credentials Sreya / demo-sreya or Sai / demo-sai. These are demo fixtures committed to the repo, not production accounts.

To run the production shape locally — one process, API and SPA on one origin:

npm run build
npm start        # http://localhost:8787

Or use the isolated smoke target, which mirrors the Render boot exactly but against a throwaway temp data directory, so your real ~/.duogrow is never touched: 

npm run smoke:isolated

03Architecture

            dev                                  production
  ┌──────────────────────┐              ┌────────────────────────────┐
  │ Vite :5173  (SPA)    │              │  Node :PORT                │
  │   proxies /api  ─────┼──┐           │    Hono app                │
  └──────────────────────┘  │           │      /api/*     routes     │
                            ▼           │      /*         web/dist   │
  ┌──────────────────────┐              └────────────┬───────────────┘
  │ Node :8787  (API)    │                           │
  │   Hono + SQLite      │                    SQLite + uploads
  └──────────────────────┘                     ($DATA_DIR)

In development Vite owns the SPA and proxies /api and /uploads to the API. In production the same Hono process serves web/dist as static files, registered after the API routes so /api always wins.

Static serving is gated on the --serve-web argv flag rather than NODE_ENV, and serve-static is loaded by dynamic import(). Both details are deliberate: a static import pulls the module into tsx watch's file-watch set, where it can wedge the dev watcher before the server ever binds.

Partner sync is 3-second polling, not websockets. Sessions live in sessionStorage, which makes them per browser tab — that is what lets you demo both sides of a duo in two tabs of one browser.

08Database schema

SQLite at $DATA_DIR/duogrow.sqlite, WAL journal, foreign keys enforced. Every CREATE is IF NOT EXISTS and migrations run at import, so booting an old database upgrades it in place.

Two legacy tables, ai_usage_daily and ai_project_usage_month, still exist but are drained by a one-time migration into the pseudonymous pair above. That migration is the reason a delete-and-re-consent cycle cannot be used to reset quota: the retained counter is keyed by a hash that survives the deletion, and it holds no prompts, replies, or raw identifiers.

api/client.ts is the single network chokepoint: it prefixes /api, reads the session token from api/tokenStore.ts, sends it as x-session, and on a 401 resets the hash to #/. It throws a typed ApiError carrying the status plus, for AI limits, a reason and retry. The multipart helper deliberately omits Content-Type so the browser sets its own boundary.

Hooks

  • usePolling — interval fetch returning {data, error, isLoading, refetch}. Pauses while the tab is hidden and refetches on return.
  • useCountUp — animates a number to its target, snapping instantly under prefers-reduced-motion.
  • usePrivateProofUrl — fetches authenticated proof bytes into a revocable object URL, since proof media is no longer a public path.

10The two AI systems

These are separate products with different providers. Confusing them is the single easiest mistake to make in this codebase.

Proof verification — Anthropic

Reads uploaded proof images. Configured by ANTHROPIC_API_KEY. Falls back to a deterministic demo verifier. This is the only component that ever sees proof bytes.

DuoGrow AI coaching — OpenAI

Daily plan, Duo Reflection, POTD tutor, insight explain, ephemeral chat. Configured by OPENAI_API_KEY. Text only. Never receives proof media or proof detail.

Consent

Coaching is off by default. A person must opt in before their account can request anything. Duo Reflection additionally requires current consent from both members, and either partner can revoke it in a single save, which immediately blocks new requests. The displayed mode is derived from live server provider availability on every settings response, never from a stale saved value.

What actually gets sent

The browser cannot supply any context payload — the server builds it from an allow-list. General coaching gets numeric goal targets, allow-listed module status/value fields, and aggregate weekly progress. Insight Explain gets only numeric score and risk signals; verifier narratives are never forwarded. POTD Tutor gets the current problem's title, body, topic, and difficulty. No proof media, file paths, user ids, duo ids, or session tokens ever reach the coaching provider.

Live calls use the OpenAI Responses API with store: false, no tools, a bounded output, and a timeout. A missing key, provider error, timeout, or malformed response returns clearly labelled demo content rather than pretending a live call succeeded — and a failed keyed attempt rolls its quota reservation back first.

store: false is not a Zero Data Retention claim. It asks the Responses API not to store that response. Provider retention, abuse monitoring, and eligibility for ZDR or Modified Abuse Monitoring must be confirmed in your own OpenAI account and agreement. Keep provider-side spend alerts on; the application caps are reservations, not a pricing promise.

11Security model

Credentials

Secrets are 8–256 bytes, salted and hashed with Node's async scrypt, compared in constant time. Plaintext is never stored or returned. Session tokens are stored as SHA-256 hashes, not usable raw tokens. A duplicate display name cannot mint a session, and legacy rows without a credential cannot be logged into by name alone.

Brute force and CPU

Two layers, because they defend different things:

  • Per-name attempt limiter — 10 attempts per 60s per normalized name. At capacity it keeps already-exhausted names denied rather than evicting them (evicting would let an attacker reset a blocked counter), and untracked attempts draw from a small shared per-window budget. A saturated cache therefore degrades protection to a bounded rate instead of removing it or locking everyone out.
  • Credential work gate — a per-name limiter structurally cannot throttle a flood of distinct names, and registration accepts unlimited distinct names. So both endpoints derive behind a gate capping concurrent scrypt work, refusing excess callers with a 503 instead of queueing unbounded CPU.

Proof media

The old public /uploads path is gone. Bytes are reachable only through the authenticated, duo-authorized GET /api/proofs/:id/file; a requester outside the proof's duo gets a not-found. File resolution is realpath-confined to the uploads directory. Successful responses carry Cache-Control: private, no-store and Vary: x-session so shared caches cannot serve one member's media to another.

--include=dev is not optional. Render sets NODE_ENV=production, which makes npm install skip devDependencies. Without the flag the build dies with vite: command not found.

Persistence — Litestream to Cloudflare R2

The service declares no disk:, so its filesystem is ephemeral: the database would be empty after every deploy, restart, or wake-from-sleep. Litestream closes that gap by continuously replicating the SQLite file to R2 and restoring it on boot. The seed:if-empty guard means a restored database is never overwritten.

Boot order, in scripts/litestream/start.sh:

  1. Restore from R2 — -if-db-not-exists and -if-replica-exists make a first-ever boot succeed, while a genuine failure (bad credentials, wrong bucket) exits non-zero and aborts the deploy. Booting anyway would serve an empty database, which is indistinguishable from having lost everyone's data.
  2. Seed only if the users table is empty.
  3. litestream replicate -exec "npm start", so Render still supervises one foreground process.

Four variables switch it on: R2_BUCKET, R2_ENDPOINT, R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY. With any of them missing the script skips Litestream, runs exactly as before, and says so loudly — so the service stays deployable before the bucket exists.

The 1-second default would have cost money. Litestream syncs every 1s out of the box. That is ~2.6M Class A operations a month against R2's 1M free allowance — the default alone pushes the account into paid overage. The config pins sync-interval: 60s, about 43k/month or 4% of the allowance.

The trade is bounded data loss: an instance that dies mid-minute loses up to 60 seconds of writes. Storage is a non-issue — a few MB of SQLite plus three days of daily snapshots against a 10GB allowance.

Native shells (iOS + Android)

The same SPA is wrapped by Capacitor. Both native projects live under web/android and web/ios and are committed; the copied web assets inside them are generated and gitignored. Build with: 

npm --prefix web run mobile:sync      # build + cap sync
npm --prefix web run mobile:android   # open in Android Studio
npm --prefix web run mobile:ios       # open in Xcode (macOS only)

Three things differ from the web build. Requests are cross-origin, because the webview serves from capacitor://localhost (iOS) or https://localhost (Android) — both on the server's CORS allow-list. The API origin must be set at build time via VITE_API_BASE_URL, since a relative path resolves against the app bundle. And the session token persists through Capacitor Preferences rather than sessionStorage, which a webview discards on teardown.

PhoneFrame is replaced by NativeShell on device: the hardware already provides the bezel and the OS the status bar, so the simulated ones would be a fake phone drawn inside a real one. Only the chrome changes — every screen is identical.

Android builds on any OS; iOS needs a Mac. The Xcode project is generated and committed so a Mac can build it immediately, but compiling and signing iOS requires macOS, and putting it on someone's iPhone requires the Apple Developer Program at $99/year. Android has neither constraint — a signed APK builds on Windows and can be shared directly.

14Gotchas

Hard-won details that will otherwise cost you an afternoon.

A blank Today screen usually is not a bug

usePolling pauses while document.hidden is true. If the tab is not focused and compositing — very common under headless or automated browsers — the screen sits on grey skeletons forever and /api/today is never requested. It looks exactly like a broken deploy. Keep the tab visible, or force it: 

Object.defineProperty(document, 'hidden', { configurable: true, get: () => false })
document.dispatchEvent(new Event('visibilitychange'))

--env-file does not override real env vars

Node fills in only what is missing. A variable already present in the process environment beats the file — which is precisely why harness:isolated can hand a temp DATA_DIR to a server whose .env also declares one. Relying on the opposite will silently point a "safe" run at your real database.

API_PORT outranks PORT on purpose

The browser-preview harness injects PORT=5173, which would otherwise steal the API's port. Keep API_PORT=8787 locally and leave it unset on Render. Also note Number(API_PORT || PORT) || 8787 silently falls back to 8787 for a non-numeric or zero value.

Sessions are per tab, and the cache is the source of truth

On web the token persists in sessionStorage, so two tabs are two independent sessions — that is what makes the two-person demo possible in one browser. A second tab will not inherit your sign-in.

At runtime, though, tokenStore reads from an in-memory cache, not from storage. Writing to sessionStorage from the console therefore does nothing until the next reload — and worse, a running app whose cache is empty will poll unauthenticated, take a 401, and clear the value you just wrote. Sign in through the UI, or write the value and reload immediately.

The cache exists because native token storage is asynchronous while every request builds its auth header synchronously. hydrateToken() is awaited in main.tsx before the first render: a screen that mounts mid-hydration reads an empty token, which is indistinguishable from being signed out, and would bounce a signed-in person to onboarding.

Multipart is buffered before the cap is checked

The 5 MB proof and 10 MB POTD limits are applied after the body is fully read into memory. The JSON routes use a streaming bounded reader that cancels early; multipart does not. Worth knowing before exposing uploads to untrusted traffic.

Demo mode is the default, everywhere

No keys means no billable calls — the deterministic verifier and demo coaching keep the whole product testable offline. GET /api/health reports the active proof mode and the Profile screen shows it. Verify this before any demo you do not want to pay for.
